problem: A developer portfolio is usually a template with screenshots, and it does not show how its author works. I wanted the site itself to be my main frontend work sample, so a recruiter or a tech lead could open the repository and find the same rigor I would bring to a product, in Spanish and English, fast on a mid-range phone and accessible to anyone.
responsibilities:
  - Designed the visual identity and the design system on tokens, with contrast checked by tests.
  - Defined the layered architecture and the rules that enforce it on every pull request.
  - Built the pages, the case studies with diagrams drawn from data, the command palette and the chat.
  - Set up delivery on Cloudflare Workers, CI with its budgets and operations with monitoring and runbooks.
constraints:
  - A mostly static site does not justify servers or databases that need upkeep.
  - Every page must load fast on a phone with a slow connection, with its own fonts and images.
  - Bilingual content, with neither translation falling behind the other.
  - Projects built for employers cannot reveal internal systems or real data.
decisions:
  - title: Static Astro with React islands
    rationale: Almost the whole site is content, so it ships as HTML without JavaScript, and only the interactive parts, such as the chat or the command palette, hydrate when they are needed.
    alternatives:
      - A React single-page application
      - Next.js rendering on the server for every visit
  - title: A layered architecture even for a small site
    rationale: Domain, use cases, infrastructure and interface are separate, and two independent tools reject any import that crosses a boundary in the wrong direction.
    alternatives:
      - Organizing by folders and trusting discipline
  - title: Projects are typed content, not pages
    rationale: Each case study is a file validated by schema and by domain rules, including the architecture diagram, which is described as data and drawn accessibly in both languages.
    alternatives:
      - An external CMS
      - A hand-written page per project
  - title: Measure performance as a visitor gets it
    rationale: Lighthouse runs on the build served with Brotli, the way Cloudflare serves it, and an earlier check fails on render-blocking stylesheets, images that download with the page or HTML over its budget.
    alternatives:
      - Measuring uncompressed HTML on the preview server
      - Checking performance by hand before each release

outcomes:
  - The site is in production in two languages, with every page above its performance budget and no axe violations.
  - Adding a project touches no code, and an incomplete translation or an internal detail does not pass the content tests.
  - The repository tells its decisions through ADRs and runbooks, so it can be reviewed the way work is reviewed on a team.
lessons:
  - I would measure performance with compression from day one, because measuring uncompressed HTML cost several CI rounds for changes that were fine.
  - I would set per-page style budgets before the redesign, not after, so render-blocking stylesheets do not move halfway through.
