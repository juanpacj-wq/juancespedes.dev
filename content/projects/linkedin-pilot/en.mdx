problem: The official LinkedIn API cannot write to a profile or apply to jobs, because real access requires a partner program and not even partners can edit work experience. I wanted an AI assistant to do that work with my own session, without storing my password and without surprise actions.
responsibilities:
  - Designed the split between reading and writing and the form engine.
  - Implemented the MCP server, the CLI and the reusable answer bank.
  - Published it with installation and diagnostics docs, plus an emergency exit to finish any flow by hand.
constraints:
  - There is no official write API, so the only way in is the real interface.
  - The interface changes its structure and CSS classes without notice, and is served in the account's language.
  - No action visible to other people can happen without explicit confirmation.
  - Sign-in is not automated, because that triggers blocks and would require storing the password.
decisions:
  - title: Read through the internal API, write through the interface
    rationale: The internal API the page itself uses returns the profile and job postings as structured data in a single call, with the same browser session. There is no endpoint for writing, so the interface is used, and if one path fails the other takes over.
    alternatives:
      - Scrape the HTML for both reading and writing
  - title: Fields identified by their visible label
    rationale: The form engine reads each control's accessible name and matches it against a bilingual glossary, so it survives HTML changes and works whether the account is in Spanish or English.
    alternatives:
      - CSS class selectors
  - title: One engine for the profile and for applications
    rationale: Editing a profile section and filling in an application are the same problem, a form with fields. A single piece solves both, and a new section is supported without code changes.
    alternatives:
      - A hand-written flow for every form
  - title: Dry run by default and explicit confirmation
    rationale: Actions other people can see require confirmation, and applications first run as a dry run to review pending questions before submitting.
    alternatives:
      - Execute whatever the assistant asks for directly

outcomes:
  - An assistant can update the whole profile, engage with other people and complete applications with the user's real session.
  - Direct browser tools make it possible to finish any failing flow by hand, without editing the project.
  - The code is public, with installation and diagnostics documentation.
lessons:
  - I would set conservative daily limits and pauses between actions from day one, because platforms detect automation patterns even when the session is real.
  - I would add tests against saved real pages to catch interface changes before they break in use.
