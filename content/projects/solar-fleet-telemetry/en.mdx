problem: An energy group installed solar systems on social housing rooftops, aiming at thousands of homes. Output sat in two micro-inverter vendor platforms, one with no public API and one with a paid API whose cost grows with the energy produced. The business needed each home as a plant, joined with its customer master list, in Power BI and in SQL for its analysts.
responsibilities:
  - Designed the dimensional model (five dimensions and four fact tables) and the medallion architecture across two destinations.
  - Built the collectors for both platforms and the real-time channel that replaced the paid API.
  - Audited a colleague's prototype for that channel, corrected how it read the data and took it to production.
  - Deployed and run the system on a Linux server with systemd services, alerts and a watchdog that emails.
constraints:
  - Neither platform offers an API meant for this use, and the paid one used up its trial quota.
  - The Fabric capacity is corporate and shared, and it was down for weeks for reasons outside the project.
  - Analysts query PostgreSQL while the ETL writes, on a database behind a private endpoint.
  - No real data about homes, contracts or devices may leave the client's environment.
decisions:
  - title: A home is a plant, identified by its contract
    rationale: A mass rename in the vendor apps erased the installer's naming convention. Anchoring identity to the grid operator contract keeps surrogate keys stable even when names change.
    alternatives:
      - Keep using each plant's name in the app
  - title: A free push channel instead of the paid API
    rationale: The paid plan cost in the tens of thousands of dollars a year and grew with output. The push channel costs nothing; the contractual risk was documented and accepted by the business.
    alternatives:
      - Pay for the platform's enterprise plan
      - A collector on each home's local network
  - title: An hour with no reports closes only if the channel was listening
    rationale: With pushed data, receiving nothing can mean the listener was down. An hour closes only when heartbeats cover it, and session edges are marked as estimated, with no false zeros.
    alternatives:
      - Treat missing reports as zero output
  - title: One watermark per destination
    rationale: Fabric and PostgreSQL each advance with their own mark. When the shared Fabric capacity was down for weeks, PostgreSQL stayed current and Fabric caught up without losing data.
    alternatives:
      - A single mark for both destinations

outcomes:
  - Output from both platforms reaches one model every three hours, on Fabric and on PostgreSQL, with 1,498 plant-hours equal to the source apps.
  - The real-time channel replaced the paid API at zero cost, and its gold layer matches the main ETL's cell by cell.
  - A lock incident that left the analysts without service was fixed with materialized views, and their metrics query went from 3 hours to 12 ms.
  - A weeks-long outage of the shared Fabric capacity cost no data, because each destination keeps its own progress.
lessons:
  - I would measure each source's cost per unit of energy produced from day one, not per device, since that is what made the paid API unworkable as the fleet grew.
  - I would separate the ETL's writes from the analysts' queries sooner, since one TRUNCATE queued behind a long query blocked everyone.
