problem: The mine's management follows daily operations (coal produced and shipped, overburden, lost hours, crushing, pumping, stockpiles and plans) on an Excel dashboard fed by two weighbridge databases, four capture workbooks and a tracking app. The company asked to move it to Power BI on its Microsoft Fabric platform without changing the figures the team already knows.
responsibilities:
  - I documented the current system (daily log, dashboard, capture forms and app) and took the calculation rules the Excel left ambiguous to the team until they were confirmed in writing.
  - I designed the star model and built it in bronze, silver and gold layers following the methodology and naming of the company's data platform.
  - I verified every layer with local Spark against the Excel dashboard and with parity tests against Fabric.
  - I ran Fabric from the terminal with the Fabric CLI and the Fabric MCP server, connected to Claude Code, to create, import, run and check pipelines without going through the portal.
  - I wrote the requirements analysis document for the users' approval.
constraints:
  - The new dashboard's figures must match the Excel ones, except for changes the team approves.
  - The capture workbooks stay in a folder on the internal network, and Fabric reads them through an on-premises gateway.
  - The methodology, naming and folders of the company's data platform were already set.
  - The weighbridge databases hold drivers' personal data, which must never reach the model.
decisions:
  - title: Pipelines as code, uploaded with the Fabric CLI
    rationale: The queries of each layer live in versioned T-SQL files, and three Python generators build the 10 pipelines, with 78 copies and a failure alert per copy. The Fabric CLI imports them and the Fabric MCP server lets the assistant inspect and run the workspace. It saved me several hours compared with configuring the 158 activities by hand in the portal, and a query change is applied by regenerating, not by repeating clicks.
    alternatives:
      - Configure every copy activity in the Fabric portal
  - title: Specification in Spark, production in T-SQL
    rationale: The model was written and verified first with Spark 3.5 on a local replica. It was then translated to T-SQL to follow the platform's methodology, and a parity test compares both versions table by table, column by column.
    alternatives:
      - Write straight in T-SQL and verify only in the final report
  - title: Full reload on every run
    rationale: The weighbridge corrects tickets from earlier days, so an incremental load by date would miss those corrections. The five bronze pipelines reload everything in about 13 minutes.
    alternatives:
      - Incremental load by ticket date
  - title: Named columns in the bronze copies
    rationale: The weighbridge copies read with a query that names every column and leaves the drivers' personal data out from the first layer.
    alternatives:
      - Copy whole tables and clean them in silver

outcomes:
  - Bronze and silver run in Fabric, with 23 bronze and 30 silver tables verified against the local replica, and gold is on its first run.
  - With the rules confirmed in writing by the team, 24 of 24 dashboard indicators return the expected value when recomputed with the model.
  - The Direct Lake semantic model, the report and hourly orchestration are still to come. The project is ongoing.
lessons:
  - I would have installed the Fabric CLI and MCP server from day one. I started using them once the model was verified, and they sped up exactly the most repetitive part.
  - I would ask for the platform's naming document from the start. Since there was none, it had to be inferred from another workspace.
