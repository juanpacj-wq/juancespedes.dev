problem: Operations needed to see, on a single screen, the actual output of four generating units against the market operator's dispatch, and the existing readings depended on a centralized system that was a single point of failure.
responsibilities:
  - Designed direct meter reading, per-period energy integration and the comparison against market dispatch.
  - Built the Node.js backend, the React dashboard and the Python service that feeds the data lakehouse.
  - Statistically validated the backup meters and documented the sign convention of each metering point.
  - Run two production instances, one per plant, from the same build.
constraints:
  - Readings every 2 seconds without losing integrated energy if the service restarts.
  - Two plants with different sign conventions depending on the metering point.
  - A failed meter must not pollute the totals with false zeros.
decisions:
  - title: Read the meters directly over Modbus TCP
    rationale: Removes the single point of failure and the automated browser from the deployment, and makes the latency of every reading measurable.
    alternatives:
      - Keep scraping the centralized system's web interface
  - title: Null means no reading, never zero
    rationale: Telling missing data apart from a zero value makes a failed meter detectable instead of reporting zero generation. The rule lives in a domain module shared by the backend and the dashboard.
    alternatives:
      - Fill missing readings with zero
  - title: Statistical validation before using the backup meters
    rationale: A one-hour parallel capture with bias, p95 and integrated energy criteria proved the backup meters are interchangeable.
    alternatives:
      - Assume the backup meters read the same
  - title: One build for two plants, configured at load time
    rationale: Each plant's branding and unit order are read from a configuration file at runtime, so a fix ships once and serves both.
    alternatives:
      - Compile a separate dashboard per plant

outcomes:
  - Operations sees on one screen the actual output of four units against dispatch, with a projection for the current period.
  - The single point of failure is gone and read latency dropped from about 1.1 s to 15 to 25 ms (p50).
  - After a restart, the service rebuilds closed periods from the database and loses no integrated energy.
  - The same telemetry feeds a corporate Power BI report without touching the dashboard.
lessons:
  - I would measure latency and the rate of null readings from day one; those figures justified the protocol change and would have brought the decision forward.
  - I would keep a single meter-reading service that publishes to both consumers, instead of maintaining the same topology in Node.js and in Python.
