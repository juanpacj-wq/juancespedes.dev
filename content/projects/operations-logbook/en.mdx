problem: Operations staff at two thermal power plants kept their shift logs in Excel workbooks. Information was scattered across files, closing a shift depended on each person's discipline, and the official daily reports were assembled by hand by copying cells.
responsibilities:
  - Gathered requirements with shift supervisors, operations engineers and chemists, and turned them into a domain model of shifts, logbooks and role-based permissions.
  - Designed and built the frontend, the backend, the database and the corporate sign-in integration.
  - Deployed and run the system on a company Linux server, with nginx, systemd and an update script with built-in checks.
  - Documented 71 architecture decisions and drove an in-house security audit until 38 of 39 findings were closed.
constraints:
  - Users on 24-hour shifts whose operating day crosses midnight.
  - Mandatory corporate sign-in with role-based access.
  - Self-hosted server on the corporate network, behind a firewall that inspects TLS.
  - Minimal third-party dependencies to keep auditing and maintenance simple.
decisions:
  - title: Shifts as a business entity, closed atomically
    rationale: Closing a shift freezes the team roster into an immutable snapshot, so history does not change when staff changes later.
    alternatives:
      - Store loose events and rebuild shifts at query time
  - title: Real time over WebSockets with origin validation
    rationale: Several people work on the same shift at once; changes arrive instantly and origin validation prevents connection hijacking.
    alternatives:
      - Poll the server every few seconds
  - title: In-house .xlsx reader and writer on top of zlib
    rationale: The official report had to match the Excel template exactly without adding large libraries to a backend that has only 6 production dependencies.
    alternatives:
      - Use a third-party spreadsheet library
  - title: A tested data contract with the generation dashboard
    rationale: Another production system consumes the logbook events. A contract test fails if either side changes the shape of the data, and each system writes only to its own schema.
    alternatives:
      - Let the dashboard read the logbook tables directly
architecture:
  summary: Each operator's browser talks to a Node.js API over HTTPS and WebSockets. The API stores everything in SQL Server, runs scheduled jobs that close shifts and ingest plant data, and exposes a data contract to the generation dashboard.

outcomes:
  - Both plants log their shifts in the application, with each shift's history frozen when it closes.
  - The official daily report comes out of the data in the template's format, with no cells copied by hand.
  - The generation dashboard consumes logbook events through a tested contract, without touching its tables.
lessons:
  - From day one I would prioritize the tests that protect dangerous invariants, such as never deleting data from a real plant, over overall coverage.
  - I would move the scheduled jobs into a separate service earlier, so the API can restart without pausing plant data ingestion.
