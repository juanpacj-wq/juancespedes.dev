problem: The previous site was four separate WordPress installations, one per language and domain, hosted by a third party. Content was outdated, the English version was not maintained, and the site did not meet Colombian transparency (Law 1712 of 2014) or accessibility (Resolution 1519 of 2020) requirements.
responsibilities:
  - Extracted the Figma design and the old site's content with my own tools, and replicated them page by page.
  - Built the block theme, two plugins and the engine that generates the English pages.
  - Wrote the server provisioning, the deployment and the hardening harness, and coordinated certificates, DNS and the web application firewall with the infrastructure team.
  - Drove an internal security audit with more than 100 findings to closure and supported the external penetration test.
  - Prepared the production acceptance record, with 9 test cases and 35 pieces of evidence, generated by code.
constraints:
  - The communications team edits content on its own, and the editor cannot break the design.
  - Mandatory transparency and WCAG 2.2 AA accessibility compliance for a public website.
  - Company-owned infrastructure, behind a corporate web application firewall.
  - Self-hosted fonts and assets, with no third-party services collecting visitor data.
  - Zero broken links during the migration, because the old addresses had to keep working.
decisions:
  - title: Git as the single source of truth
    rationale: The WordPress admin only edits content. Block structure is locked, and the menu and the route table live in the repository and are seeded with idempotent scripts.
    alternatives:
      - Configure the site from the admin panel
  - title: An in-house engine for the English version
    rationale: The 67 English pages are generated from the Spanish ones with a per-page translation catalog. Both versions share the same structure, and a check blocks publishing a page whose translation is incomplete.
    alternatives:
      - A multilingual plugin with pages duplicated by hand
  - title: Reproducible deployments with automatic rollback
    rationale: Each deployment packages an exact commit with its checksum, runs validations, backs up the database, switches versions atomically and rolls back on its own if verification fails. It rolled back 4 times in production with no downtime.
    alternatives:
      - Upload files over FTP or edit on the server
  - title: A content security policy measured with a browser
    rationale: The CSP was built by crawling 137 routes at two widths with a real browser and fixing until there were zero violations.
    alternatives:
      - Copy a generic CSP and loosen it every time something broke

outcomes:
  - The site went to production with an acceptance record signed by the business and technology areas, after 9 test cases run against production.
  - All 76 legacy addresses redirect with a 301 and no link was left broken.
  - The communications team publishes and updates content without depending on a developer.
  - The site was verified at 27 screen widths, from 360 to 1,920 px, and accessibility issues were tracked in a log with measurements and their fixes.
lessons:
  - I would set up the security harness and the CSP measurement in the first week; much of the closing work came from checks that could have been automated earlier.
  - I would ask for a test environment with the same network and firewall as production from the start. Several differences between the two environments showed up at the end of the project.
